A Tale of Three Pascals
.pp
.fi
Suddenly, we SS-50 bus users who have in the past had good reason to feel
slighted for lack of software to run on our systems find ourselves with three
Pascal compilers available to us.	"Which one should I buy" is probably the
question of the day.	Maybe you are thinking that you won't buy any of them
for a while until the reports are all out and you can choose.	This review
will examine all three, list their strengths and weaknesses, and give you an
opportunity to choose the one best suited to you and your applications.
.pp
First of all, let's make it clear that there is no obvious "champ" and no
"turkey" among the three.	Just in case you hadn't run across all of the
implementations, I should first give you their names and histories.	The
first Pascal compiler to hit the market (nearly 2 years ago) was one from
Lucidata, a small company now located in Cambridge England.	They released an
integer only version first, but very soon introduced a version with REAL
variables.	Very recently they have upgraded the package with the addition of
the scientific functions.	The latest release for the 6809 is called version
3.9.	The Lucidata offering is a P-code compiler, which means that it
generates a Pseudo code that is "run" by a small interpreter at run time.
This produces the most efficient code generation (in terms of bytes of code
generated for a given program), but the execution time suffers slightly.
.pp
The second to appear was a compiler from OmegaSoft in Sunnyvale CA.	This one
is a "native code" compiler.	It generates an Assembler source code file that
is then assembled.	The advantage is faster execution.	OmegaSoft uses their
own assembler (written in Pascal) that is a relocatable version, and a
linking loader also written by them.	The relocatable assembler and linking
loader allow a Library feature that only compiles the run time packages
called by the user program.	The result is a rather small run time package
for small programs.	The assembler, however is slower than it might be.	The
Pascal compiler, which translates source text into assembler source files,
however, is very fast.	
.pp
The third to appear was the TSC Pascal.	This too is a native code compiler.
In general, the runtime package must be used as a single "chunk".	It is
possible to reset a pointer in the runtime package and write over some of the
package if, for example the scientific functions are not required.	To do
this it is necessary to load the program and runtime package, get into the
monitor mode, and read a pointer, then write into the Heap pointer.	This
could be done within the user program if necessary.	TSC Pascal has Peek and
Poke functions that would allow such modifications.
.pp
Just to keep from repeating names excessively here, lets refer to the three
as TSC, LUCI, and OMS in the remainder of this discussion.	In order to
evaluate these with respect to size of object code, and speed of execution, I
compiled the same program (almost) in all three, and made comparisons.	The
Programs for LUCI and OMS are identical.	TSC for some reason decided to put
some declarations at the front of the user program (that could in my opinion
just as well have been handled by the compiler directly).	These make it
necessary NOT to have the standard first line 'PROGRAM PROGNAME
(PARAMETERS);'.	With that line deleted or made into a comment line,
the program compiles in TSC as well.	Table 1 shows the results.	The
program is a reasonably efficient way to find prime numbers (a favorite of
mine).	

.pp
Some conclusions are obvious.	The P-code version compile is a single step
operation, and it is faster.	The user code generated by the P-code version
is smaller than TSC and OMS by 25\% and 33\% respectively, but execution
takes more than twice as long.	The TSC runtime package size shown is that
obtained by truncating the runtime package as described above.	If this is
not done, the package is nearly 11K.	The TSC compiler makes several passes,
which makes it slower than the others.	The fact that it produces about 11\%
less code than OMS, indicates that the multi-pass compiler does more
optimization than the OMS version.	This is also reflected in the execution
time being shorter by about the same ratio.	The TSC assembler is very fast
compared to the OMS.	Remember that the TSC is not relocatable.	A portion of
the assemble time in OMS is the linking loader time, and library file scan
time.	The OMS compiler is lightning, but the slower Assembler makes the
overall time about the same.	LUCI is a single step, two pass compiler and it
doesn't have to be assembled, so the overall time is shorter than the other
two. OMS has a feature that overcomes the long Assembler time.	It has a
DEBUG feature that is essentially a fast one-pass assembler.	You type
DEBUG,FILENAME and your program is assembled to memory only (no disk file).
The program may then be run (see below) and tested.	DEBUG assembled the
PRIMES program in 9 seconds from the time I hit return after typing the
command.	This places the total Compile-Assemble time at 29 seconds for
debugging purposes!
.pp
An interesting relationship may be seen in the table.	Perhaps it is
coincidental, but it seems reasonable that spending more time in compiling
should result in a more efficient execution time.	If doubling the compile
time resulted in halving the execution time, the compile time execution time
product ought to be about constant.	Deviations from a constant would tend to
be a sort of figure of merit for the compiler, the smaller the product, the
better.	The product for TSC is 9154, for LUCI 8710, and for OMS 9420. The
variation is less than 13\% for these three.	The number obviously would
change for another program, but would be a useful comparison value for
several compilers running the same program.
.PP
It is extremely informative to compare the sizes of the files generated by
the compilers for the sample program here.	All of course have the same
source text file of 7 sectors.	Both TSC and OMS generated an assembler
source file of 18 sectors!	Both LUCI and TSC generated an output .BIN file
of 3 sectors! LUCI's P-code interpreter is 40 sectors, and TSC's runtime
subroutine package is 42 sectors!	OMS produces a final .BIN file with the
needed runtime subroutines linked, of 11 sectors. LUCI produces a runnable
file using the RUNCMD feature, of 16 sectors.
.pp
Regarding ease of operation, assuming you have a source text file ready, you
run LUCI by typing RUN,PASCAL,FILENAME and LUCI generates a user binary file
for you.	You then type RUN,FILENAME and the program is run.	The LUCI
runtime package that is loaded by RUN is about 9.5K long, but LUCI has a
special RUNCMD function that loads the runtime package and the user program
and then tells you the starting, ending, and transfer addresses so you can
save the program with runtime package, to a file that will load and run.	I
had done this for the test above.	Apparently the runtime package for LUCI is
loaded somewhat selectively, and saving the loaded program allows you to take
advantage of this.	
.pp
TSC is about as easy to use.	You simply type the command
PASCAL,FILENAME,<options> and the compiler makes its several passes and
exits having generated an Assembler source file with the same filename and a
default extension of .ASM.	You must then use the standard assembler to
assemble the program, typing in the standard command line for it.	If you
have used the assembler at all, this will come very naturally to you.
.pp
OMS is a little more complicated in terms of procedure, but is more flexible.
You first compile the text file, just as with TSC.	The Assemble Link process
is more complicated, but OMS has made it as easy as possible.	A utility
called BUILDIT has been provided.	BUILDIT prompts you for information, such
as the filename, program name (if different), and where and how much memory
space to allocate for the DATA stack and the SYSTEM stack.	It then
automatically generates some command files.	You then type CHAIN,FILENAME
and sit back and watch the process on the CRT.	Several files are generated
on the disk, but most are very short.	You have the opportunity to specify
the loading and linking of any Assembler procedures or functions you might
have written to perform special functions etc.
.pp
All three systems are very clean in operation and allow many options that are
specified simply.	OMS and LUCI allow you to generate a "listing file" that
has the default extension .OUT.	You can then list your program later if
there are no corrections made.	TSC and OMS add line numbers to the source
listing so that if you list the program to the CRT while compiling, the error
messages may be associated with a line number, a help in finding the line for
editing later.	LUCI puts the P-code relative program counter at the
beginning of each line as it is compiled.	The runtime error messages include
the P-code Program counter, so the error may be traced to a line of the
program.	TSC has an option that allows inclusion of line numbers in the
output, so that runtime error messages can include the line number at which
the error occurred.	OMS has a special DEBUG mode.
By including debug options in the compile command line, you can run your
program, insert breakpoints, look at values of variables, etc.	The DEBUG
assembler has some limitations
but in general, it is quite useful.	It assembles a program very quickly, and
along with the very fast compiler, makes debug of a medium sized program very
fast.
.pp
I should here mention that all three implementations have some standard
features not implemented, and all have "extensions" of their own.	I have no
problem with any of these, but the out and out deviations from the standard
bother me a little more.
Perhaps it is time for a quick rundown of which of the standard Pascal
features are implemented by each.	It will probably be easier to
mention those not implemented.	TSC includes a copy of the Jensen and Wirth
standard as part of the program manual for their Pascal.	A bothersome
deviation from the standard in my opinion is the omission of the first line
of the program.	An obvious way to maintain compatibility with other Pascal
compilers is to "brace" the first line so as to make it a comment.	Doing
this for the program illustrated here causes a "difference" of two characters
from the version that is correct for the other two compilers.
TSC also has the limitation that their implementation
doesn't automatically convert integers to real numbers in 'mixed mode'
arithmetic, where for example, you have a real variable divided by an
integer.	You must use REAL / CONV (INTEGER), ie. an internal conversion
procedure that you MUST use.	The Standard, and the other Pascals make the
conversion automatically when necessary.	
.pp
In an attempt to see just how inconvenient this deviation would be, I decided
to try running LUCI's demonstration program called REALS.	This program
demonstrates the use of real variables but it has a great deal of mixed mode
arithmetic included. LUCI doesn't require declaration of the standard files
INPUT and OUTPUT in the first line of the program, though the compiler
doesn't object if they are there.	The demo program didn't have them	so I
added them and compiled the demo in OMS with no further changes.	I note at
this point that I could have gone back and recompiled it with LUCI with no
changes, and that it complies fully with the Jensen Wirth Standard.
Forgetting moemntarily about the CONV function, I commented out the PROGRAM
name line and tried compiling it with TSC.	I got 10 error messages.	I had
to look at the listing and decide which were the offending INTEGER variables
in the mixed mode expressions and add the CONV(	) around each of them.
This, to my surprise didn't remove all the error messages.	I found that I
had to go make the constants REALS too by changing, for example, 12 to 12.0.
On the fourth try, I finally managed to make the TSC compiler happy, and it
finished without errors.	Surprise!	16.8 digits are nice if you are working
with the national debt, but they certainly slow down operations using REAL
variables.	The times to run the Demo program were:

Obviously the number of digits accuracy of the 3 compilers cause a
rearrangement of the order of their execution speed when doing calculations
that use REAL variables.	Perhaps another test should be run using CHAR
variables to see how they work in this area too.	I would include a listing
of REALS, but Lucidata is in England, and I don't want to hold this until I
receive permission from them.	Perhaps Frank will publish it in a future
Newsletter.
.pp
Moving on to another area, all three compilers handle disk files
somewhat differently, though rather similarly.	TSC requires you to include
the disk file names of any files the program will	use in the command line,
as does LUCI.	OMS on the other hand, allows the program to ask you for a
filename, or for you to have included a filename within the program at your
option.
.pp
LUCI and TSC have implemented dynamic variable allocation via pointer
variables, the Heap, and the procedures MARK and RELEASE.	OMS has not
implemented these yet though an update release is promised that will have
this and RECORD types which it does not now have.
TSC has implemented variables of type RECORD, and the
WITH statement.	LUCI has the RECORDS but not the WITH.
OMS is the easiest to link to an external Assembler procedure or function,
though LUCI and TSC allow this too. In the OMS version, all parameters are
passed to the assembler routine on the U stack, and parameters are returned
in the same way.	This included both values and pointers.	
TSC has a mechanism for passing parameters between Pascal programs that
results in a useful CHAIN feature for running multiple programs.
.pp
OMS has several useful STRING procedures and a data type STRING implemented.
The string procedures are analogous to those found in BASIC.	These are
not part of the standard, but are extensions.	LUCI has a most interesting
extension regarding SCALAR variables.	When you define a SCALAR data type, you
list all the "values" it may take:	DAYSOFWEEK =
(mon, tue, wed, thu, fri, sat, sun);	If now, you define a variable DAY :
DAYSOFWEEK;	you can assign it a value of, for example, 'sat'.	In standard
Pascal, to write the value of DAY to the terminal you must use:
.nf
	CASE DAY OF
	mon : WRITE ('MONDAY');
	tue : WRITE ('TUESDAY');
	wed : WRITE ('WEDNESDAY');
	thu : WRITE ('THURSDAY');
	fri : WRITE ('FRIDAY');
	sat : WRITE ('SATURDAY');
	sun : WRITE ('SUNDAY')
	END;

.FI
LUCI has implemented the obvious.	Since the program must recognize 'mon' as
a valid value of DAY, why not be able to use WRITE (DAY); and have it output
the proper value.	LUCI has done it.	This is a very useful extension.
.pp
Though TSC's implementation has the two most obvious deviations from the
standard, it
is the most complete implementation.	LUCI is next, claiming that they have
included all the standard features that are practical in a microcomputer
version without getting unreasonable with regard to size.	OMS has the least
features implemented, but is promising a very nearly FULL implementation
of the standard with no deviations, only extensions, in the near future!
By very nearly full, I mean that they will not implement DISPOSE, for the
dynamic variable implementation, but use MARK and RELEASE.	Both TSC and LUCI
have implemented dynamic variables this way.
.pp
Perhaps I should point out here that extensions need not be used in any
program where "portability" between different compilers is important. If you
are going to publish a program, for example, stick to the standard features
only.	If the program is for a specific use and compatiblilty is not
important, use any extension that makes the program more efficient.	The
example program given here uses only standard features and is therefore
compatible with all three compilers.
.pp
One other point deserves mention here.	TSC has "16.8 digit" REAL variables.
LUCI has 9 full digits, and OMS has 7, with at least 6 digit accuracy
for scientific and trigonometric functions.	All have 16 bit signed two's
complement INTEGER representation which limits integers to the range of
-32767 or -32768 to +32767.
.pp
TSC has a predeclared variable TYPE called ALFA that is a string of length
10.	LUCI has an ALFA type that is a string of length 8 characters.	OMS has
a type STRING [n] where n, the maximum length of the string may be user
specified. LUCI has a
type BYTE also.	LUCI and OMS allow data type HEX.	TSC has PEEK and POKE for
communication with hardware ports etc.	I should point out that they have
both single and double byte Peek and Poke commands, both of which are useful.
OMS and LUCI allow declaring variables at absolute addresses.	
That means you can declare an INTEGER or HEX variable at the address
of a port, (or BYTE in LUCI) and by assigning a value to that
variable, you can write to the port, etc.	LUCI and OMS have provision for
imbedding compiler instructions in your source text file to turn the listing
function on and off.	All three allow, in addition to the alphanumeric
characters in Identifiers, an underline character (_) so that you may
separate the multiple words as in DAYS_OF_WEEK in order to make compound
variable names more readable.	LUCI has recognized that this is non-standard
and provided an overlay that will enable this feature.
.pp
OMS produces programs that are directly rommable.	Both LUCI and TSC stick
variables immediately above the program in memory, though LUCI has another
package that may be used to make their code rommable.
.pp
LUCI inputs characters from the terminal "interactively", that is, if you
have READ (CH); where CH is a variable of type CHAR, LUCI only waits for the
character.	OMS will accept a stream of characters until a CR is typed, and
then read the first character in the buffer.	TSC has it both ways.	They
have a command called UNBUFFER which makes input interactive, and one called
BUFFER which makes it like OMS.	We have discussed the difference with OMS
and then read the Jensen Wirth standard.	It would appear that OMS was
correct.	We, however needed the interactive mode, and wrote our own
assembler function in 4 lines to allow immediate acceptance of a single
character.	All of the versions, of course wait for a CR when inputting
numerical values.
.pp
Generally in the past,
compilers that have a large runtime package have
been sold with a restriction that the purchaser may not sell or give away the
runtime package.	TSC's manual plainly states that your program after
compilation and assembly is yours, and you may sell it or give it away, but
you may not include any portion of their runtime package unless you make a
license arrangement with them.	In other words, if your friend (or customer)
has their Pascal, he also has the runtime package, and you need only send
your program to him.	Anyone not having TSC Pascal, however, wouldn't be able
to use your programs.	LUCI had a similar arrangement until recently.	Now
their official policy is that if you use the RUNCMD as described above, and
generate the complete "runnable" combination of your program and their
runtime package in binary file form, you may sell it or give it away with no
license restrictions.	OMS specifically states in their software agreement
that there are no restrictions on the sale of programs generated by their
compiler, and no further license agreements necessary for the sale of
programs that include part or all of their runtime package in binary form.
.pp
There are some practical considerations involved.	OMS requires a minimum of
32K memory, and it is possible to run on a 5" disk system, I checked with
OmegaSoft and they confirmed that it is supplied on a 5" disk.	
The Compiler, Assembler, Linking loader and Runtime
Library files plus the couple of utilities and Debug, nearly fill a standard
single sided single density disk (327 sectors total) which can make operation
with a two drive system difficult for a large program.	The Assembler
source file that the compiler generates is quite a bit larger than the
original source text file, and a large program can overflow a small disk.
.pp
LUCI will run on a 5" disk system nicely (Runtime plus compiler, 165 sectors).
It has a "paging
mode" feature that allows it to run in as little as 12K of memory.	Even if
you have 32K, a very large program might resort to the paging mode during run
or compilation.	In this mode, portions of the program are automatically
loaded from the disk as they are needed.	This of course slows down the
execution, but it does allow you to run very large programs!	As a matter of
interest, LUCI sort of bootstrapped their compiler.	That is, the Pascal
compiler is written in Pascal.	
.pp
TSC makes no
mention of the hardware requirements in their manual.	I assume that they
require 32K to 56K of RAM.	Their compiler only (with all the files for the
several passes) uses 340 disk sectors!	You need the Assembler and their
runtime file PRUN which is 42 sectors to run the program.	This is still
managable on a 5" system, since you could use a "compiler" disk for just the
compile function, then switch to your system disk which would have to have
the Assembler and the PRUN file.
.pp
All of these suppliers are reliable.	TSC and Lucidata have proven records of
quality and customer service, and OmegaSoft was very responsive to my reports
of a couple of bugs in an early copy I received.	Much to my surprise, they
took to heart my comments about the long Assemble time (originally much
longer) and made major improvements in that area too.	
.pp
Well, there it is.	As the man said, "You pays your money and you takes your
choice".	I will probably hear from all three of the suppliers that I left
some nice extension of theirs out of this discussion.	I have to say here
that they are all very good.	If I were to have to list the
best and worst features of each, I would have to submit the following:

Perhaps a word or two about Pascal itself is appropriate here.	Pascal is not
a difficult language to learn.	The manuals for all of the above mentioned
compilers assume that you know Pascal.	There are many good books available
from which you can learn all the standard features.	The manuals therefore
concentrate on the deviations and extension features of the respective
implementations.	If you are interested in learning Pascal before deciding to
buy a compiler, two excellent books are, "A Primer on Pascal" by Conway,
Gries, and Zimmerman, published by Winthrop Publishers of Cambridge Mass.;
and "Pascal An Introduction to Methodical Programing" by Findlay and Watt,
published by Computer Science Press, Inc. of Potomac, Md.	The Primer doesn't
conver the entire standard Pascal, but a subset that leaves out a few of the
more advanced features.	It probably is the best choice for a beginner.	For
coverage of the features not covered there, the Findlay and Watt book is an
excellent second book.
.pp
From personal experience, I can say that Pascal is easy to learn if
you have a firm grasp of BASIC.	When I received the first compiler, I
translated a 13 page or so BASIC program to Pascal and had it running in two
days.	I can't say I clearly understood all the workings of Pascal at that
point, nor that I now have the whole thing down pat, but I don't think you
have to understand every feature to begin using a language.	You begin to see
the Philosophy of Pascal very soon.	It is a very "regular" language, and its
syntax soon becomes second nature.
