A RELOCATABLE FILE FORMAT FOR SK*DOS

	"By
	Jack W. Crenshaw


INTRODUCTION


I am currently working on a linker for use with SK*DOS. The
availability of such a linker will permit the use of modular
programming techniques by allowing us to develop library subroutines
in separately assembled or compiled subroutines and libraries.

This document describes the proposed interim file format for the
linker. Anyone who is developing system software for SK*DOS is urged
to use the same format, so that all SK*DOS tools will be compatible.

This format is an INTERIM standard. It is especially chosen to be
useable with the existing SK*DOS loader and the assembler ASM, which
is not a "relocating assembler." Specifically, the format is chosen so
that it is possible to use ASM to generate relocatable files.

Remember, the format is PROPOSED. If anyone sees something wrong with
the format, or has suggestions as to how to improve it, it is not too

FUNDAMENTALS

The term "linker" is a bit of a misnomer, since the typical linker
really performs two separate and distinct functions:

	o Linking

	This is the function we normally think of when we think about
	linkers at all.	The linker resolves references to various entry
	points, so that when the program is completely linked, all
	references (jumps and calls) have the correct addresses associated
	with them. To accomplish this, the linker loads all the needed
	files, and keeps track of the address for each entry point. After
	all files have been loaded, the linker goes back and fixes up all
	the addresses.

	o Relocation

	The final output of the linker is a single COM file, suitable for
	loading by the SK*DOS loader. To obtain it, the linker loads the
	needed modules into successive locations. As each module is moved
	into place, it may be necessary to alter the jumps and calls
	internal to the module to keep them correct in the module's new
	location relative to the beginning of the file. The linker must
	also produce an output file which can be correctly relocated as it
	is loaded by the SK*DOS loader.

	It should be noted that in SK*DOS, a COM file is not loaded to a
	fixed location. Rather, its load address will depend upon what
	drivers or other software are already resident. For that reason,
	SK*DOS convention requires that all executable programs be written
	as position-independent code ... a requirement not too difficult
	to meet with the 68000 instruction set.	Nevertheless, for special
	situations the SK*DOS loader does provide for a limited degree of
	relocation, so the linker will, too.

To perform these functions, the linker needs extra information not
normally provided by the assembler. In particular, it needs to know
the names of all the entry points external references, and it needs to
know where to find them in the code module. It also needs the
information related to relocation. The format described here provides
that information. The format is specifically chosen so that this extra
information can be generated by ASM using data declarations (DC's). In
that way, we can go ahead and use the existing tools. For the moment,
there is no other way to generate files in this format. Later on, we
fully expect that preprocessors, relocating assemblers, and compilers
will be developed that generate the necessary data automatically.


THE FORMAT

The default extension for relocatable files is REL. A REL file will
contain the following information, in the order indicated:

	< entry point name list >
	< entry point address list >
	< external reference name list >
	< transfer vector >
	< code length >
	< executable code >
	< relocation vector >

The content and format of each of these fields is described below.


Entry Point Name List

This is a simple list of ASCII names, one for each entry point. For
our purposes here, an entry point is described as the beginning of a
subroutine that is in the current module, and that is to be accessible
(callable) by other programs or subroutines contained in other
modules. Note that by this definition, a main program is _NOT_ an
entry point, since it is not callable by others. SK*DOS already has a
mechanism (the transfer address) to find the main program entry point,
and this same mechanism is retained by the linker.

Each entry point name is an ASCII string, exactly eight characters
long, of upper case characters. It is left justified ... names shorter
than eight characters should be padded with spaces. The list is
terminated by a null >>WORD<<. Note that the use of a word terminator
avoids even/odd address difficulties.

Example: Suppose we have a main program with two subroutines, FOO and
BAR, that we want to be visible from outside. The assembler code to
generate the Entry Point Name List would be:

---------------------------------------------------------------------

ORG 0	ORG >>MUST<< be zero

* Entry Point Name List


DC.B 'FOO	'	First entry name

DC.B 'BAR	'	Second entry name

DC.W 0
Terminator
---------------------------------------------------------------------


Entry Point Address List

Associated with the Entry Point Name List there is also a
corresponding Entry Point Address List. This is a simple list of
***16-bit*** words, each giving the address of the corresponding entry
point, relative to the beginning of the file. Recall that the origin
of the file is always zero, so the relative address in this case is
the same as the "absolute" one. There must be an exact one-for-one
correspondence between each entry name and its corresponding address.
The address list is also terminated by a null word. Note that this is
not necessary ... by the time the linker gets to this point it has
already read the name list and so it knows how many entries to expect.
The null terminator serves as a bit of insurance to qualify the file
and make sure it's in a valid format.	For our example above, the code
to generate the Entry Point Address List would be:

---------------------------------------------------------------------
* Entry Point Address List


DC.W FOO
Note it's an address, not a string

DC.W BAR

DC.W 0
Terminator
---------------------------------------------------------------------


External Reference Name List

This list is just like the Entry Point Name List: a list of
eight-character ASCII names, terminated by a null word. An external
reference is required for any subroutine that is called within the
current module, but which does not appear in it.

Example: Suppose our main program calls three subroutines, SUB1, SUB2,
and SUB3 (very original, eh?). The assembler code to generate the
External Reference Name List would be:


---------------------------------------------------------------------
* External Reference Name List


DC.B 'SUB1	'	First external reference name

DC.B 'SUB2	'	Second external reference name

DC.B 'SUB3	'	Third external reference name

DC.W 0
Terminator
---------------------------------------------------------------------


Transfer Vector

Now we get to the tricky part of the format. When devising the format,
I needed a way to generate linkable code without having to first write
a relocating assembler. The solution was to borrow from a technique
used in early mainframe systems, which also had to make do with
available tools. The trick is that calls within a given module to
external subroutines don't actually call the subroutine directly, but
rather call dummy subroutines which are actually far jumps (JMP's) to
the actual subroutine. This causes a bit of overhead since all
external calls must go through an extra jump, but it greatly
simplifies the process of generating the relocatable file. Of course,
it also makes the linker simpler, smaller, and faster.

The Transfer Vector, then, is a series of JMP instructions, one for
each external reference. Each entry must have a label, since that is
the way it is referenced from within the module. For the sake of
consistency, this list is also terminated by a null word. Again, a bit
of redundancy for insurance.

The address field of each JMP is arbitrary, since it will be patched
by the linker to point to the real subroutine. A value of zero should
be used.

Example: for the External Reference Name List used above, the code to
generate the Transfer Vector would be:

---------------------------------------------------------------------
* Transfer Vector

SUB1	JMP 0	Dummy address filled by linker
SUB2	JMP 0
SUB3	JMP 0

DC.W 0
Terminator
---------------------------------------------------------------------


Code Length Word

This is a single word given the length in bytes of the file, from the
beginning of the file (including all previous fields) to the end of
the executable code. This length is needed to be able to distinguish
the executable code from the Relocation Vector which follows it. The
assembler can be used to generate this code with a command of the
form:

---------------------------------------------------------------------
* Code length


DC.W THEEND
---------------------------------------------------------------------

where THEEND is a label which immediately follows the executable code.


Executable Code

This, of course, is the usual set of machine-language instructions. It
is generated from the assembler using normal programming techniques.
Immediately following the executable code should be a label for the
the end of the code, such as the THEEND label used above.

---------------------------------------------------------------------
THEEND	EQU $	Marks the end of code segment
---------------------------------------------------------------------


Relocation Vector

Now we get to the most difficult part of the format to generate using
the normal ASM assembler. Fortunately, it is often also not needed.
Remember that the convention for SK*DOS programs is to use fully
position-independent code. As long as this rule is followed, there
need by no entries in the Relocation Vector. This feature is only
provided for those special cases in which relocation is in fact
required.

The relocation vector is a simple list of addresses, just like the
Entry Point Address List. Each address is a 16-bit word, giving the
address, relative to the beginning of the module, of a 32-bit LONG
word that needs relocation. Typically, these longwords will be the
address fields of instructions that were written using the absolute
long addressing mode. After the program is completely loaded and
linked, the linker will adjust these addresses and issue the
appropriate code in the output COM file to insure proper relocation
when SK*DOS loads the program.

As usual, the list is terminated by a null word. Note that the address
zero cannot ever be a valid address for relocation.

Unfortunately, there is no easy way to get the assembler to generate
this vector. The easiest, which is a bit messy but works well enough,
is to assign a label to EVERY instruction written in absolute mode
(that should surely be enough to discourage the indescriminate use of
the feature!). Then the address field of the instruction will
(usually) be addressed two bytes beyond the label.

Example: Suppose our main program has two instructions written in
absolute long addressing mode. We assign a label to each instruction,
thus:

---------------------------------------------------------------------
LBL1	JMP FRANK
References needing relocation

.
LBL2	JSR GEORGE

.

.
FRANK	.

.
GEORGE	.
---------------------------------------------------------------------

Then, the Relocation Vector can be coded as follows:


---------------------------------------------------------------------
* Relocation Vector


DC.W LBL1+2	Note: address of address field

DC.W LBL2+2


DC.W 0
Terminator
---------------------------------------------------------------------

A word of warning: The offset of 2 bytes is correct for JMP and JSR
instructions, but can be different for other instructions. The user
should be certain exactly where the address to be relocated is.

In the future, it is expected that automated tools will be developed
to ease the generation of this part of the format. Until then, we'll
all have to make do.

Any of the fields described above may be null, i.e. have no entries,
if entries are not called for. However, the terminating null words
must still be present to signal the beginning of the next field. Thus,
an ordinary COM file is _NOT_ a legal REL file (though there is no
reason why it should be. Although the following program is sort of
worthless, it does give an example of the simplest REL file one can
have:

---------------------------------------------------------------------

ORG 0	ORG >>MUST<< be zero

* Entry Point Name List (null)


DC.W 0
Terminator

* Entry Point Address List (null)


DC.W 0
Terminator

* External Reference Name List (null)


DC.W 0
Terminator

* Transfer Vector (null)


DC.W 0
Terminator

* Code length


DC.W THEEND

* Executable Code

In other words, a REL file will be at least 6 words longer than a
corresponding COM file. This doesn't seem like too much of a price to
pay for the flexibility of relocatable modules.


WHAT ABOUT DATA?

In all the previous discussions, there has been a tacit assumption
that the only kind of linking one would want to do is that for jumps
and calls. That is, in fact, one of the main uses of linking. However,
there are times when we would like to access external DATA, as well.
Although this need is not specifically addressed in the description
above, it is worth pointing out that the format does give all the
information needed to access such external data.

Remember, there is nothing in the design that really distinguishes
between labels that point to code and labels that point to data. When
the linker has does its job, the address fields of the jumps in the
transfer vector will contain the actual addresses of all data items
identified as "entry points" in the Entry Point Name Lists. Thus a
module will have all the information it needs to access that data,
although it needs to be done with one level of indirection. We
just must be careful to use only the ADDRESS field of the
corresponding jump in the Transfer Vector. Don't execute the jump by
mistake!!!

The following example gives the idea:

---------------------------------------------------------------------
DATA	JMP 0	Entry in the transfer vector

.	Linker fills in the true address

.

.
* Fetch the address field into an address register
* (Note that we use position-independent addressing)


MOVE.L DATA+2(PC),A0	Fetch the address field

* A0 now contains the address of the data


MOVE (A0),D0
Then do whatever with it

.

.

---------------------------------------------------------------------


CONCLUSION

I hope that this document will be helpful to those involved in the
development of system software for SK*DOS. Again, remember that this
is merely a PROPOSED, INTERIM standard until a relocating assembler
becomes available. In good time, we can expect a new standard format
that has more flexibility than the one proposed here. In the meantime,
the format described should meet 99% of our needs. Please contact me
at the address given previously, if you have any comments or
suggestions.
